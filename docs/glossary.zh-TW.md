# 詞彙表:中文側的用詞裁定

## 這張表放決定,不放現況

這張表只放**裁定**:一個概念在中文側規定怎麼寫、綁哪個英文詞、為什麼。
它**不放**「現在哪一份檔案寫了什麼」——那種句子由 `make bilingual`
(`scripts/check_bilingual.py`)每次執行時重新算出來,不寫進表裡。

這個分工是被三輪修訂逼出來的。這張表會促成另外六份中文文件的修訂,而修訂
改掉的正是那些句子,**所以它會以自己造成的修訂速率腐爛**:

- 第一輪:一條 gate 裁定引了 `env.zh-TW.md` 的一句話當佐證,而那句話正是
  同一輪依這張表改掉的。
- 第二輪:立了下面〈錨點規則:這份表怎麼指向別的檔案〉,規定只用檔名＋節名。
  同一輪寫進去的一個節名從來不存在於被指的那份檔案裡——**新規則宣稱最安全
  的那種錨點,在引入它的那一輪就已經失效**,而且沒有任何東西會發現。
- 第三輪:一個被裁定禁用的中文詞,全樹只剩下裁定它的那一列自己還留著;
  表上卻仍寫著「某某檔現在用了它」。

每一輪都修掉當時發現的腐爛,每一輪都長出新的。再修一輪實例只會買到下一輪,
所以改的是分工:

| 這張表寫下的(裁定,不腐爛) | `make bilingual` 每次重算的(觀察,會腐爛) |
|---|---|
| 概念、規定的中文寫法、綁定的英文詞(第四欄「為什麼」是註解,不維護,見下) | 表裡引用的檔名與節名解不解得開 |
| 哪些寫法被禁用 | 被禁用的寫法在中英兩側全樹還有沒有命中 |
| 哪個中文寫法綁哪個英文 join key | 中文寫法出現的每一節,對側有沒有那個英文詞 |

判準很好用:理由欄可以寫「『行程』在中文第一義是旅遊行程」——那是**關於中文
的事實**,不會因為誰改了哪份檔而變假;不可以寫「`optimize.zh-TW.md` 現在寫的
是 X」——那是**關於別份檔案現況的描述**,而那份檔案正被這張表促成的修訂改動。

檢查器只做機械可查的事:字串比對與錨點解析。它查不到語意,也查不到一個符號
有沒有真的在首次出現處被定義——那仍然只有下一次冷讀看得見。

### 前三欄是有效內容,第四欄是註解

一條裁定需要理由,而好的理由天然會去引用語料。前面兩輪都明文規定理由欄不准寫
語料現況,兩輪都還是寫出來了。那不是執行不力,是在跟寫作的本性打架;所以這一輪
不再多下一道同樣的禁令,改成把欄位分級:

- **前三欄(概念／English original／規定的中文寫法)是這張表的有效內容。**
  禁用詞掃描、join key 綁定、逐列欄數、裁定數樓地板全部作用在它們身上,
  `make bilingual` 每次執行都重算一次。
- **第四欄「為什麼」是寫給人看的說明,不維護。**它可能過時,
  **不視為本專案的現行宣稱**。發現它過時**不必修**——要修當然可以,
  但沒有人有義務,而且不修不算缺陷。

理由就寫在這一節開頭那份紀錄裡:每一輪都修掉當時的理由欄腐爛,每一輪又長出新的
——它以語料的修訂速率腐爛,而第四欄沒有任何機械檢查看得見它,所以腐爛只會累積,
不會被攔下。假裝維護得了它比誠實宣告不維護更糟
——**一個看起來被維護的過時說明,比一個標示為不維護的過時說明更會誤導**,
因為前者會被下一個讀者當成現行宣稱拿去用。

**兩個例外仍然留在有效內容裡**,因為它們不是說明,是宣稱:

- 理由欄裡的**數值與公式**是本專案的技術宣稱。它不能因為寫在第四欄就免於
  更正:發現它和 `RETRACTIONS.zh-TW.md` 裡的裁定衝突,那就是缺陷,要修。
- 理由欄裡**寫成錨點形式的語料引用**照樣由錨點檢查驗證。那道檢查不因為這條
  降級而放寬:錨點是機器看得見的,而機器看得見的東西就留在有效內容裡。

## 這份表是怎麼長出來的

不是先想好一份「應該要有的術語」再填進來的,是**從證據長出來的**。

這個 repo 的六份中文對照(`env`、`dependencies`、`journal`、`optimize`、
`RETRACTIONS`、`tolerance`)寫完之後,各交給一位沒有參與撰寫、也沒讀過英文
原檔的讀者冷讀,並且被問了同一個問題:**「把每一個你必須用猜的詞列出來。」**
六份總共回報 95 個。這份表收的就是那 95 個裡面站得住的那些。

這個做法是刻意的。寫的人看不到自己造的詞——那些詞是在寫的人自己的脈絡裡
長出來的,對他而言每一個都理所當然。**這是位置決定的,不是用不用心決定的**;
所以入口佇列只能是冷讀者的猜測清單,不能是作者的回憶。

證據來源(這六份就是被冷讀的六份):
[`env.zh-TW.md`](env.zh-TW.md)、
[`dependencies.zh-TW.md`](dependencies.zh-TW.md)、
[`journal.zh-TW.md`](journal.zh-TW.md)、
[`optimize.zh-TW.md`](optimize.zh-TW.md)、
[`RETRACTIONS.zh-TW.md`](RETRACTIONS.zh-TW.md)、
[`tolerance.zh-TW.md`](tolerance.zh-TW.md)。

一個維護上的但書:這份表本身也是「同一件事寫兩份」,中英兩側各一。
`make bilingual` 查得到它們的結構有沒有對上,查不了意思有沒有對上。

### 錨點規則:這份表怎麼指向別的檔案

這份表會促成別份文件的修訂,而修訂改掉的正是句子。**所以錨點不能是句子。**

寫法只有一種,因為它必須被機器解析:

- 檔名寫成反引號包起來的路徑,例如 `env.zh-TW.md`(路徑相對於本檔所在目錄,
  所以主 README 要寫成 `../README.md`,不然會解到 `README.md`);
- 節名用書名號夾起來,而且**緊接在檔名後面**(中間只容許「的」與空白);
- 指同一份檔案裡的節,就只寫節名不寫檔名,例如本頁最後一節〈怎麼維護〉。

`make bilingual` 會把每一個都解開:檔案要存在,節名要真的是那份檔案的標題。
解不開就 exit 1,並印出那份檔案裡最接近的幾個標題,讓下一個人有得修。

**不拿逐字引句當佐證。**引句解析不了,也註定被下一次修訂改掉。

唯一的例外是**被裁定的詞本身**。那些不是錨點,是裁定的對象;它們寫在
「不要用「…」」裡,而檢查器正是靠那個寫法認出禁用清單的。

**「為什麼」欄要指語料,也只能用上面那個形式。**理由欄裡凡是提到這個 repo 的
語料——某份檔案怎麼寫、兩個詞在哪裡一起出現、哪一段是誰的節標題——就必須照上面
那三點寫成錨點(反引號路徑＋書名號節名),讓錨點檢查看得見。寫不成那個形式的
觀察(「兩者在某份文件裡相鄰出現」、「整篇都在講 X」)不是寫得不夠好,是不該
寫:那是現況,會被這張表促成的修訂改假,而且沒有任何機制會發現它變假了。刪掉,
理由欄只留站得住的那半。

這條**不管**關於中文本身的事實。「『行程』在中文第一義是旅遊行程」不是語料
觀察,誰改了哪份檔都不會讓它變假,所以不需要錨點。分辨法只有一句:**這句話要
讀這個 repo 才驗得了,還是懂中文就驗得了?**

## 一、一實多本:同一個概念,repo 裡出現過兩個以上中文名

這一節比其他節值錢。單一檔案裡難懂的詞,讀者卡一次就過去了;**同一個東西
在不同檔案有不同名字,會讓讀者以為那是兩個東西**,而且錯誤會隨著檔案增加
而放大。

第三欄若以「…」開頭,表示這條**宣告了 join key**:那個中文寫法綁第二欄的
英文詞,檢查器會逐節查。以反引號開頭的表示裁定是保留英文,沒有中文 join key。

| 概念 | English original | 規定的中文寫法 | 為什麼(機制與碰撞) |
|---|---|---|---|
| 把設計畫到設計像素網格上 | rasterize | `rasterize` | 這批文件通篇在講 grating(光柵),任何照字面譯出來的中文名都會和它撞在一起。**不要用「光柵化」**;**不要用「重新離散成幾何」**,那是另造的第二個名字 |
| 服役中／實際拿來跑正事的那一套 | production | 「正式運轉」(首次出現附 production) | 這條問的是**是不是正式在用的那一套**(那支 driver、那組相依),不問規模。**不要用「產線」**——那兩個字在中文第一義是工廠裡的製造流水線,而這個題目本來就在講 SOI/DUV 製程,讀者會直接接到晶圓廠那條線上去 |

| spack 的 package 定義檔 | recipe | `recipe` | 保留原文,和 `spack.yaml`、`spack.lock` 這些你會在工具訊息裡看到的字串一致。**不要用「配方」**——中文第一義是食譜或藥方,而且它會和「預設設定」那個意思混起來 |
| 一次執行,以及它落地的那個目錄 | run | `run` / `run` 目錄 | 「輪」會被讀成迴圈的第幾次(iteration),而 run 是一次執行。**不要用「正式輪」** |

## 二、碰撞:這個中文詞在別處已經有意思

碰撞是最危險的一類,因為讀者**不會發現自己讀錯了**——句子讀起來很通順,
只是講的是另一件事。第四欄就是那個「另一件事」。

| 概念 | English original | 規定的中文寫法 | 中文既有義(會被誤讀成什麼) |
|---|---|---|---|
| 兩義:L0 的 GPU 驅動程式,與把優化迴圈串起來跑的主程式 | driver | `driver`(首次出現指明是哪一種) | 中文第一義是「裝置驅動程式」,會把概念欄那兩義都吸到 GPU 那一邊去;只靠上下文分辨會錯 |
| pytree 的葉節點陣列 | channel | pytree 的葉陣列 | 這是光子學專案,channel 的第一直覺是波導通道或波長通道 |
| 從機制本身逐項推算,不引用既有結論 | from first principles | 「從頭逐項清點」 | **不要用「第一原理」**——那四個字在光子學與材料模擬語境裡是 ab initio 電子結構計算,是個很硬的現成含意 |
| FDTD 模擬的整個計算區域 | scene | 「模擬場域」(首次出現附 scene) | **不要用「場景」**——中文日常指場合、情境,讀起來像在講故事 |
| eroded / nominal / dilated 三個密度場 | three-field | 三個密度場(eroded/nominal/dilated) | 「場」會撞上整篇在講的電磁場。**不要用「三場」** |
| spack recipe 裡的 `version()` / `depends_on()` / `variant()` | directive | 宣告(directive) | 中文「指令」第一義就是命令列打的那一行(shell command);再拿同一個詞去指 recipe 裡的 `version()`,一個詞會扛兩個意思 |
| 機器所在的計算中心 | site | 計算中心 / 機房(site) | **不要用「站台」**——那兩個字中文第一義是月台或網站,後面再接「設定」,整句會被讀成網站設定 |
| 兩義:`make` 的目標,與 spack 的 `target=` CPU 微架構 | target | Makefile target(相對於 spack 的 `target=`) | 同字兩義,而中文只有「目標」一個詞接得住,譯了就分不出是哪一個。首次出現各自標明 |
| 作業系統裡一個獨立執行的程式實例 | process | `process` | 中文「行程」第一義是旅遊行程,所以保留英文;而 `dependencies.zh-TW.md`〈授權加起來是什麼〉整段論證掛在「程式碼有沒有進到同一個 process」上,讀錯等於整段讀錯 |
| CE 頻譜的峰形,以及欄位名 `ridge_lam_um` 裡的同一個字 | ridge | 「頻譜峰形」 | **不要用「稜線」**——中文第一義是山脊;而且這裡的 ridge 也不是脊狀波導(ridge waveguide) |
| 拿另一個來源核對同一個數字 | reconcile | 核對 / 驗證 | **不要用「對帳」**——那是會計用語 |
| GitHub 依 tag 自動打包的原始碼 | archive | `archive` | 中文「封存」的語感會蓋掉「壓縮包」的意思,而中文同樣會把 dist tarball 叫成壓縮檔,兩者得分辨得開 |
| β 隨迭代升高的預定表 | schedule | `schedule` | 中文「排程」第一義是 Slurm 那種工作排程,而這一條講的是 β 怎麼升,譯成「排程」會被讀成另一件事 |
| Boost Software License | BSL-1.0 | `BSL-1.0`(首次出現補「(Boost)」) | 和 **BUSL**(Business Source License,**不是**開源授權)字形極近。授權名讀錯會把整個授權結論弄反 |

## 三、保留英文原詞

這一節的「規定的中文寫法」欄就是英文原詞本身——裁定是**不要翻**。理由多半是:
中文沒有對應的既有說法,硬造一個只會多一個要解釋的詞;或者它就是你在
`uv.lock`、工具訊息、上游文件裡會看到的那個字,譯掉之後反而查不到。

| 概念 | English original | 規定的中文寫法 | 為什麼不譯 |
|---|---|---|---|
| 把上游那個 release 的程式碼複製一份進本 repo 自行維護,不再走套件安裝 | vendor | vendor(動詞) | 中文沒有「vendor 某物」這個動詞,而「廠商／供應商」是反向誤導:它指的是**我方**把別人的碼收進來 |
| spack 的虛擬套件:一個抽象名字(例如 `mpi`),由多家實作去滿足 | virtual | virtual | 譯「虛擬」會被讀成虛擬機或虛擬環境 |
| 系統上已經存在、spack 直接拿來用而不自己建的套件 | external | external | spack 專有名詞,譯掉就對不回 `spack.yaml` 裡的那個鍵 |
| 你自己在 `spack.yaml` 的 `specs:` 點名的那幾個,相對於被遞移拉進來的 | root spec | root spec | 兩個字都是 spack 術語,拆開譯任何一半都會失去對應 |
| 把抽象需求解成一組確定版本與編譯選項,以及做這件事的求解器 | concretize / concretizer | concretize / concretizer | 結果寫進 `spack.lock`;動詞與名詞要一起收,漏收名詞的話讀者會以為那是別的東西 |
| spack 的建置選項(`+python +mpi` 那一串) | variant | variant | **不要用「變體」**——那兩個字中文第一義是病毒或生物學上的品系 |
| `pyproject.toml` 裡宣告的一組選用相依,`--extra gpu` 就是裝那一組 | extra | extra | Python packaging 的專有名詞。譯成中文會被讀成「額外的 GPU」 |
| `[build-system].requires` 點名、負責把原始碼變成 wheel 的那個套件 | build backend | build backend | 它自己要另外下載,這正是它會在離線機器上絆倒人的原因;譯掉就查不到上游文件 |
| 把專案原地連進環境而不複製,改原始碼立刻生效 | editable install | editable(`-e .`) | 旗標本身就叫 `-e`,譯名和旗標對不起來 |
| 一份宣告內容的清單檔 | manifest | manifest | 中文沒有一個同時涵蓋 packaging 與 spack 兩種 manifest 的既有詞 |
| conda 用來區分「同一個版本、不同建置」的那串識別碼 | build string | build string | 它是 conda 輸出裡逐字出現的欄位 |
| 把每個套件的確切版本寫死的檔案(`uv.lock`、`spack.lock`) | lockfile | lockfile | 檔名本身就是 `.lock` |
| MPI 的平行 process 編號;`mpirun -np 2` 會看到 2 個 | rank | rank | 中文「秩」是線性代數的 rank,撞得很硬 |
| JAX `while_loop` / `scan` 每一步攜帶的狀態 | carry | carry | 它是 API 的參數名 |
| JAX 把輸入 buffer 就地讓給輸出重用,省一份記憶體 | donation | donation | 字面「捐贈」完全無從入手;它是 `donate_argnums` 的那個 donate |
| 不從 wheel 裝、直接在本機從原始碼編譯出來的那一層(L2:Meep、MPI、HDF5) | native | native(層) | 它是 `dependencies.zh-TW.md`〈Native 層 —— Meep 環境〉這個節標題的一部分,譯掉就和對側的節標題對不起來 |
| 二進位層面的介面約定 | ABI | ABI | 縮寫在中文技術寫作裡也直接用;對不上的話,版本號看起來相容也還是會爆 |
| C 的標頭檔 | header | header | 可寫「系統標頭檔(header)」;單獨的「標頭」會撞上 HTTP header 與檔頭 |
| invdx 裡一個完整的題目定義(幾何＋量測＋驗收),住在 `src/invdx/problems/` | problem | problem | 它是模組名與目錄名 |
| 拿有限差分去驗 adjoint 梯度算得對不對的那道檢查 | gradcheck | gradcheck | 同時也是函式名 |

| 那一組 corner 的集合 | ensemble | ensemble | 建議整句寫成「對三個 corner 這個集合取最壞值(worst-case)或 softmin」 |

## 四、硬翻:字面翻過來,在中文不成詞

上一節是「不譯」,這一節是「譯了,但譯壞了」。共同特徵是:**中文那幾個字
單獨拿出來讀不出原意**,讀者只能靠上下文反推,反推錯了也沒有任何訊號。

被禁用的那些寫法列在「不要用「…」」裡,而不是寫成「某某檔原本寫成…」——
後者是對別份檔案的現況描述,會腐爛;前者是一條站得住的裁定,而且
`make bilingual` 每次都會回去確認它沒有復活。

| 概念 | English original | 規定的中文寫法 | 為什麼那個譯法不行 |
|---|---|---|---|
| 很多東西掛在它上面,動它會連帶壞掉一串 | load-bearing | 承重 / 撐住的東西多 | **不要用「吃重」**——那兩個字在中文是費力、角色重要,不是「很多東西掛在上面」;拿它去說「私有 API 是…的」根本不成句 |
| 多出一塊要維護、要跟著上游變的東西 | surface | 一塊要維護的東西 | 單獨一個「面」字當名詞,讀不出 surface |
| 上游官方就支援,不需要自己補 | first-class | 正式支援 / 官方就有 | **不要用「一級的」**——中文「一級」是評等或優先級 |
| 裝滿 wheel 的目錄,`--find-links` 指過去的那種 | flat index | 裝滿 wheel 的目錄(`--find-links` 那種) | **不要用「扁平索引」**——讀者只能從 `--find-links` 反推,而反推錯了沒有任何訊號 |
| 藏在某個東西底下,不在你以為的那一層 | nested | 藏在 / 巢狀在……底下 | **不要用「巢在」**——「巢」在中文不當動詞用 |
| 拿版本號當作另一件事的替身指標 | proxy | 拿版本號當替身 | **不要用「代理指標」**——會被讀成 proxy server,而且「指標」另有 metric 與 pointer 兩義 |
| 兩層的版本會愈拉愈開 | drift apart | 兩層版本會愈拉愈開 | **不要用「漂開」**——那不是一個中文詞 |
| 被當成理所當然、沒有人去驗過 | assumed | 想當然 / 理所當然 | **不要用「默認」**——第一眼會讀成「預設值」,意思正好相反 |
| 整條曲線一起上下移動,形狀不變 | shift the level | 整條曲線會整體上下移動 | **不要用「位準平移」**——「位準」台灣工程界確實在用,但搭配「平移」太抽象,讀者看不出是整條曲線 |
| 這一項要問的是另一個問題 | Ask a different question | 這一項要問的是另一個問題 | **不要用「這一格」**——那預設讀者面前有一張表格,而文中沒有 |
| 控制 erosion / dilation 的那個參數 | knob | 控制 erosion/dilation 的那個參數 | **不要用「旋鈕」**——中文讀者會去找那個實體的旋轉開關在哪 |
| 兩個差值必須恰好為 0,不容許任何數值漂移 | bit-exact contract | 這兩個差值必須恰好為 0,不容許任何數值漂移 | **不要用「逐位元契約」**——「契約」單獨出現時不透明,而這裡要說的是一個可驗的等式 |
| filter 當初就是照這條最小線寬規則做出來的 | the min-width rule the filter was built from | 這條規則當初 filter 就是照它做的 | 字面譯成「被 filter 過的最小線寬規則」語意不通:規則不會被 filter |
| 本文開頭那個數字的出處 | the motivating number | 本文開頭那個數字是打哪來的 | **不要用「動機數字」**——那四個字連在一起在中文不成詞,要展開成一句話 |
| 主 README 那條「設定檔是唯一真相來源、腳本不准自己硬寫數字」的守則 | the README's "Hard-won guardrails" | `../README.md`〈Hard-won guardrails (encoded in `engines/conventions.py`)〉 | **不要用「慣例教訓」**——英文 README 沒有叫這個名字的小節,讀者拿它去搜尋一定落空。引真正的節名,而且只引到節:「第 N 條」是序數,README 一改編號就假,錨點檢查也看不到它 |

## 五、符號與縮寫登記

這一節和上面四節性質不同:它們不是譯錯,是**符號本身要有人給定義**。

裁定只有一條政策:**這些符號在每一份用到它的文件裡,首次出現處都必須就地
定義**;這張表登記的是「定義該說什麼」,不是「哪一份還沒做到」。後者是現況,
會腐爛,而且沒有可靠的機械判準——「一段中文有沒有把某個符號解釋清楚」不是
字串比對能回答的問題,所以這裡不假裝檢查器有在管,也不在表上寫一份會過期的
待補清單。要知道哪裡還缺,唯一的辦法仍然是下一次冷讀。

| 符號 / 縮寫 | English original | 定義該說什麼 |
|---|---|---|
| θ | theta | 光纖入射角(度);θ=0 就是完全垂直入射 |
| ρ / rho | rho | 設計密度場(連續變數,見 `design_rho.npy`);`∂CE/∂rho` 就是對它求梯度 |
| η / eta | eta | tanh projection 的閾值:`eta_i`=0.5 標稱、`eta_e` eroded、`eta_d` dilated |
| h | h | 有限差分的步長;h-scan 就是掃不同的 h |
| N / T | N, T | `reversible ≈ 144·N²·T` 裡,N 是每邊的 cell 數,T 是時間步數 |
| C | C | `peak(C)` 裡的 C 是 checkpoint 數。斜率是 **268.0329 B/cell/checkpoint**,Turing 上 C=0 的截距 372.18 B/cell(Ada 的截距尚未確立)。舊的斜率已被撤回,見 `RETRACTIONS.zh-TW.md`〈2026-08-22 — checkpoint 記憶體斜率 `291 B/cell/checkpoint` 是 GiB/GB 單位標錯,不是量測被污染〉 |
| CE | coupling efficiency | 耦合效率,本專案要最大化的那個量 |
| cell / voxel | cell, voxel | 同一個東西:三維網格的一格。**統一用 voxel**;非寫 cell 不可時,首次出現要寫明「cell 即 voxel」 |
| 齒 | tooth | 光柵的週期性線條。「逐齒的線寬敏感度」就是逐條線去看線寬變化的影響 |
| OOM | out of memory | 記憶體爆掉 |
| PML | perfectly matched layer | FDTD 的吸收邊界 |
| FD | finite difference | 有限差分 |
| G0–G5 | gates | `make gates` 依序跑完的六道驗收關卡 |
| V3 / V5 | — | 和 G0–G5 **是兩套不同的編號**,不可互推;V5 不是 G5 的筆誤。每一份同時用到兩套的文件,首次出現都要就地說明 |

## 六、中文獨有的增補:回填英文,還是宣告為本地化補強

前五節處理的是「同一件事,兩側寫得不一樣」。這一節處理另一種:**中文側有、
英文側根本沒有的段落**。那不是漂移,是譯的人順手把一個洞補起來了——問題在於
沒有人裁決那個補丁該不該也進英文側,於是每份文件都要重新決定一次。

判準只有一條:**那段內容對英文讀者是不是同樣有價值。**

- **有** → 回填英文側。它補的是文件本身的洞,只是剛好在譯中文的時候被發現。
- **沒有,它處理的是中譯特有的坑** → 宣告為**本地化補強**,只留在中文側,
  並把這個裁定寫在那段增補自己旁邊(方塊裡、或緊接的一句)。不寫的話,下一個
  人會把它當成漏譯而「補」回英文側。

把方塊拆開處理是常態,不是例外:一段中文獨有的增補裡,通常只有「為什麼會
踩到」那半是中文特有的,「踩到之後會怎樣」那半兩種語言都需要。

這一節**不列**「目前哪幾段是中文獨有的」。那是現況,而且是**這條裁定自己會去
改掉的現況**:一段被裁定回填、真的回填完之後,它就不再是中文獨有的,列在這裡
的那一行同時變假,沒有任何機制會回頭刪它。裁定跟著那段增補走,不跟著這張表走
——狀態繫在身分上,不繫在某一份副本的內文裡。

## 這份表刻意沒有收的東西

一份什麼都收的表等於沒有表,所以下面這幾類被擋在外面:

- **已經被各檔的術語方塊處理好、而且處理得一致的詞**:`module`、`view`、
  `prefix`、`spec`、`air-gapped`、`wheel` / `wheelhouse`、`drift`、`pin`、
  `transitive`、`copyleft`、`voxel`、`corner`、`requeue`、`adjoint`、`FOM`。
  這些沒有出現在任何一份冷讀的猜測清單裡——**那就是它們有效的證據**,
  再抄一份到這裡只會多一個要同步的副本。
- **一次性、和本專案詞彙無關的詞**:某條 CVE 描述裡的 `tile`、`keyring`、
  `MCP server stack`、`client SDK`。冷讀者確實卡住了,但那是那一句話要補的,
  不是專案要建立的用詞。
- **不是用詞問題、是內容缺口的項目**:冷讀者卡住不是因為某個詞譯壞了,是
  因為那份文件少講了一件事(某個欄位是什麼單位、某個門檻怎麼算)。這類不能
  用詞彙表修,只能回去改那份文件——所以**清單也不留在這裡**。逐項列出來的
  話,補完一項就假一項,而這張表沒有任何機制會知道。
- **英文側自己就有的洞**。有些冷讀發現不是翻譯造成的,而是兩側都缺
  (符號沒定義、引到不存在的節名、同一個東西英文側自己有兩種叫法)。
  **這類修的時候兩側要一起修**,只改中文側會製造新的漂移。這一條寫在這裡
  是為了讓下一次冷讀認得出這個類別,不是待辦清單。

## 怎麼維護

這份表是棘輪:只往裡加,不憑印象刪。

加一條的條件只有一個——**有人真的猜錯或猜不到**。來源是冷讀:找一位沒讀過
英文原檔、也沒參與撰寫的讀者,問「把每一個你必須用猜的詞列出來」,他列出來
的就是入口佇列。作者自己重讀找不到這些詞,那是位置決定的,不是用不用心決定的。

要改一條既有的裁定,就直接改這裡,不要在別的檔案裡另起一個新譯法。

寫的時候有三個地方會直接變成檢查:

- **禁用一個寫法**:在理由欄寫「不要用「X」」。檢查器會拿 X 去掃**中英兩側**
  全樹,豁免的只有「不要用「X」」這一串字本身,**不是整行**。同一列的理由欄裡
  再寫一次 X,就是真命中。所以裁定只點名一次,理由改用「那兩個字」「那四個字」
  帶過。豁免只有一個 token 寬是刻意的:一行寬的豁免等於允許禁用詞躲在裁定它的
  那一列自己的理由欄裡,而那正是這條規則要防的東西。
- **綁一個 join key**:把中文寫法欄寫成以「…」開頭。檢查器會逐節查:中文寫法
  出現的那一節,對側英文那一節要有第二欄的英文詞(或中文那一節自己附了
  英文原詞)。英文詞被改名而沒人來改這裡,就會在這裡爆。
- **指向別份文件**:照〈錨點規則:這份表怎麼指向別的檔案〉寫。檔案或節名不
  存在就會爆,並印出最接近的候選。

第四欄「為什麼」不在這三件事裡,也不在任何一道檢查裡:它是說明,不維護,
見〈前三欄是有效內容,第四欄是註解〉。所以改一條裁定時,只有前三欄非改對不可;
第四欄要不要跟著更新由你決定,不更新不算欠債。唯二的例外是它裡面的數值/公式,
以及寫成錨點的引用——那兩類是宣稱,照樣算缺陷。

`make bilingual`(見 `scripts/check_bilingual.py`)查的是結構與上面這三件事。
**它查不到語意**——一個詞在一份文件裡被換成同義的另一個說法、一個符號有沒有
真的被解釋清楚,是機器看不見的,只有下一次冷讀會看見。
