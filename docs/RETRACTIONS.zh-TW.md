# 撤回紀錄(Retractions,只增不改)

這份檔案記錄本專案曾經對外寫下、後來又被證據推翻的結論(寫在程式碼、文件或報告裡都算)。
條目只往下追加;**原始文字留在它原本的位置不刪不改**,就地更正時只加一條指回這裡的連結。
保留錯誤結論的完整敘述是刻意的:要讓後來的人看得出當初為什麼會相信它。

每條至少有這四個欄位:**原本的主張** / **推翻它的證據** / **更正後的陳述** /
**連帶影響**;必要時後面再接一段欄位以外的補充。

> **先講清楚一個用詞**:這裡的「撤回」撤的是**結論**,不是學術界那種**撤稿**——
> 被撤回的文件仍然留在 repo 裡、仍然可讀,只是其中某一句結論已經作廢。
>
> (**本地化補強,不回填英文側**:英文只有 retraction 一個詞,中文卻要在
> 「撤回」與「撤稿」之間先選一個,這句話是為那個選擇存在的。裁定依據見

> 寫在這裡而不寫在詞彙表裡,是因為裁定跟著這段增補走。)

## 2026-08-17 — gradcheck 失敗的成因被誤判成 float32 的 cancellation

**原本的主張**(gradcheck 的 docstring 最初就是這樣寫的;gradcheck 是拿有限差分
去驗 adjoint 梯度算得對不對的那道檢查,同時也是函式名):在 grating_coupler 的
`Device`(fdtdx 裡代表可設計區的那個物件)voxel(三維網格的一格)上,有限差分
(finite difference,FD)與 adjoint(伴隨法)對不起來,原因是「兩個幾乎相等的
float32 相減」——也就是 cancellation 造成的雜訊(兩數相減把有效位數吃掉;不譯,
以免和光學的相消干涉混淆)——而訊號下限(signal floor)取樣器(只測梯度達到峰值
5% 以上的 voxel)就是為了處理它。

**推翻它的證據**:θ=10 的第一次 run 是被一次 gradcheck 失敗中止的(voxel 213,
相對誤差 6.29%),當時跑的是正式規模(production-scale):0.8 ps、θ=10
(θ 是光纖的入射角,單位是度;θ=0 就是完全垂直入射)。我們把這次失敗**逐位元
重現**,再對步長 h 做掃描(h-scan),得到四項結果:

- 殘差隨 **h³** 縮放(h 每減半殘差 ×0.126,約當 1/8);若真是 cancellation 雜訊,
  這條線應該是平的。
- 殘差是實測 float32 雜訊本底(noise floor)的 **200 倍**。
- 用同樣那兩個 h 值做 Richardson extrapolation(理查森外推),與 adjoint 吻合到
  **0.0106%**。
- 失敗的 voxel 根本不是弱訊號:voxel 213 的梯度有峰值的 15%,是訊號下限(5%)的
  3 倍;而且 θ=10 的梯度訊號比 θ=0 還**強** 63%。

這個 h 掃描可以直接拿那次中止的 run 自己的 `cmd.txt`/`config.json` 重現;同一組
雙 h 比較現在以 `fd_consistency` 之名常駐在 `gradcheck()` 裡。

**更正後的陳述**:cancellation 雜訊這個解釋,只有對訊號下限**以下**的 voxel 才
成立(取樣器原本要做的事,它還是做得到)。合格的 voxel 在正式規模下,FD 誤差的
主導項是**截斷誤差**(truncation):run 跑得越久,FOM(figure of merit,被優化的
那個目標值)隨設計參數的變化就越振盪,f‴(FOM 對設計參數的三階導數)因此變大,
固定 h=0.05 之下的 h³ 項也跟著變大。**adjoint 從頭到尾都沒有錯。**

**連帶影響**:gradcheck 現在改用兩個 h 的 Richardson extrapolation,外加一個 FD
自洽性指標;容差與訊號下限不變。

## 2026-08-22 — checkpoint 記憶體斜率 `291 B/cell/checkpoint` 是 GiB/GB 單位標錯,不是量測被污染

**原本的主張**:三維 adjoint 的 checkpoint 記憶體模型是
`peak(C) ≈ 370 + 291·C` bytes/cell。(這裡的 checkpoint 是梯度重算用的那一種——
反向傳播時為了省記憶體而保留的中間狀態,拿時間換記憶體——不是斷點續跑用的
`opt_state.npz`;C 就是 checkpoint 的個數,cell 則是前面說的 voxel。)這個模型
擬合自三個錨點量測(1.944M cells 之下,C=10/20/28 → 5.93/11.25/15.42 GB),
而且被當成「已確認」,因為第二次推導重現了 370.1/291.3——**但那次推導用的是
同一組常數**。

**推翻它的證據**:改用來源彼此獨立的錨點重新推導一次。

- Turing 世代 GPU 上執行期的 `peak_bytes_in_use`(未受污染的量測點:C=10 跑在
  獨立的 process 裡,C=20 與 C=28 在量測當下各自都是新的歷史最高水位
  (high-water mark));
- Ada 世代 GPU 上的同一種量測;
- XLA 編譯期的 `compiled(...).memory_analysis()`(完全不執行任何 kernel)。

三者一致給出 **268.0329 B/cell/checkpoint**,相對差 1.1e-7。第四項檢查是逐一清點
fdtdx 真正 checkpoint 下來的那些陣列各占多少位元組(leaf-channel byte count:沿
JAX pytree 一路數到葉節點;這裡的 channel 指 pytree 的一個葉陣列,不是光學的
波導通道或波長通道):完整 carry 複本(carry 是 JAX `while_loop` 每一步攜帶的
狀態)有 37 個葉陣列,反向 VJP(vector-Jacobian product)還要第二份複本,再 30 個
(`src/invdx/engines/fdtdx_checkpoint_buffers.py`)。這條路徑預測出同一個斜率,
誤差 5.6e-8——5.21 億位元組裡差 29 個位元組。

那三個錨點值本身**沒有**被污染:本專案先前踩過的那個 process 層級 `peak_bytes`
high-water-mark 效應,這次不是元凶(`peak_bytes_in_use` 報的是整個 process 的歷史
最高水位,所以同一個 process 裡先前的大配置會把水位墊高,讓後面的讀數跟著偏大)。
那三個值另以獨立來源重現過,誤差 <1.5%。
錯發生在**下一步**:那三個點讀出來的是十進位 GB(1e9 位元組),但擬合出的斜率與截距
(`0.5274`、`0.670`)被標成「GiB」,換算成 bytes/cell 時乘了 2^30 而不是
1e9——這是 7.374% 的膨脹,291 與 268 的落差大半由此而來;剩下約 1.2% 來自拿三個
四捨五入到兩位小數的點去擬合,而不是用精確的位元組數。同一組擬合正確換算後是
≈271 B/cell/ckpt,已經很接近真值 268。擬合這一步不會驗證單位標籤:量測工具
(NVIDIA/JAX/XLA)吐出來的多半是位元組原始值,後面那個 `GB` / `GiB` 是**寫報告
的人**自己貼上去的。

> **單位陷阱(這條就是被它咬的)**:`GB` 是十進位的 1e9 位元組,`GiB` 是
> 2^30 = 1073741824 位元組,兩者差 7.374%——正好就是上面那個數字。中文環境
> 特別容易養成壞習慣:Windows 檔案總管和許多中文技術文章都把 2^30 直接寫成
> 「GB」,於是「看到 GB 就當 2^30」。
>
> (**本地化補強,不回填英文側**:這個方塊拆成兩半看——「踩到之後會怎樣」
> 那半,英文側的正文本來就有(7.374% 的膨脹、單位標籤是寫報告的人貼上去的);
> 只有「為什麼中文讀者特別容易踩」那半是中文環境特有的,英文側補上去沒有價值。
> 裁定依據見
> `glossary.zh-TW.md`〈六、中文獨有的增補:回填英文,還是宣告為本地化補強〉。)

**更正後的陳述**:checkpoint 記憶體斜率是 **268.0329 B/cell/checkpoint**,跨
Turing 與 Ada 一致到相對 5e-8,而且和「從頭逐項清點 fdtdx 那個 checkpoint 化的
while-loop 究竟存下哪些東西」算出來的結果對得起來。Turing 上 C=0 的截距,用同一組
乾淨的兩點資料算出來是 **372.18 B/cell**,不是 370.1;370.1 是同一個 GiB/GB bug
在同一個平台上產生的,因此它**不構成**跨架構差異的證據。Ada 的截距差異是不是真的
來自架構層級,**尚未確立**:Ada 這邊沒有來源獨立的原始兩點位元組資料,無法用同樣
的方法算一次。

**連帶影響**:任何建立在 `370 + 291·C` 上的外推都必須改用 268 重算——包括
`reversible ≈ 144·N²·T` 與 `checkpointed ≈ 291·N³·C` 在 `N* ≈ 519` cells/edge
的交叉點(N 是每邊的 cell 數,T 是時間步數)。

**另外,「多條獨立路徑吻合到 1.1e-7」這個說法本身也超出了證據能撐的範圍。**
兩條執行期路徑和那條編譯期路徑,讀的是同一份 XLA `BufferAssignment`(編譯期就
算好的那份配置表,記載每個 buffer 要開多大):執行期的 `peak_bytes_in_use` 是
記憶體配置器(allocator)的歷史最高水位,而配置器要開多大的 buffer,正是照
`memory_analysis()` 報出來的同一份配置表決定的。就「已規劃的部分」而言,它們吻合
幾乎是同義反覆(tautology)——它證明的是**沒有計畫外的額外配置**:沒有 donation
出意外(donation 是 JAX 把輸入 buffer 就地讓給輸出重用),沒有超出計畫的碎片化,
也沒有 host staging(資料繞經主機記憶體中轉)。這是真結果,但很窄。跨架構比較同理:
它顯示的是同一個記憶體規劃器(planner)在兩台機器上做了同樣的決定,不是兩次獨立
量測。**只有葉陣列位元組清點(leaf-channel count)這條路徑和 XLA 的記憶體規劃器
不共用任何前提,它才是真正的獨立檢查。**
